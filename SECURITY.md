# Security Architecture & Policies — Survetra Services

## 1. Security Philosophy & Threat Model

Security is baked directly into the architectural fabric of the Survetra Services platform. The system operates under a **Zero-Trust** model: every incoming request to administrative or mutate-state endpoints is explicitly authenticated, authorized, and logged.

---

## 2. Authentication & Cryptographic Standards

### 2.1 Password Hashing & Key Derivation
- Passwords are never stored in plaintext or reversible encryption.
- **Algorithm**: `BCrypt` with an adaptive work factor of 12 rounds.
- Each password entry incorporates a cryptographically unique 128-bit salt generated by `SecureRandom`.

### 2.2 JWT Token Lifecycle
- **Algorithm**: `HMAC-SHA256` (`HS256`) using a minimum 256-bit (64-character hex) secret key.
- **Token Validity**: 24 hours (`86,400,000 ms`).
- **Payload Claims**:
  - `sub`: Authenticated user email address.
  - `roles`: String array of granted authorities (e.g., `["ROLE_SUPER_ADMIN"]`).
  - `iat`: Timestamp of token issuance.
  - `exp`: Timestamp of token expiration.
- **Token Validation**: The stateless `JwtAuthenticationFilter` intercepts every request, validates the cryptographic signature, verifies timestamp validity, and populates the `SecurityContextHolder`.

## 3. Defense Against OWASP Top 10 Threats

### 3.1 Injection Attacks (A03:2021)
- **SQL Injection**: Prevented by design using Spring Data JPA and Hibernate. All database interactions utilize parameterized prepared statements. Raw string concatenation in JPQL or native queries is strictly prohibited.
- **NoSQL / OS Command Injection**: No dynamic shell execution or unescaped document database queries exist in the application codebase.

### 3.2 Broken Access Control (A01:2021)
- Administrative write routes (`/api/v1/admin/**`) are safeguarded by URL pattern matching in `SecurityConfig.java`.
- Role verification checks authorities before delegating execution to the controller layer.
- Public administrative registration is intentionally absent; only authenticated Super Admins can issue administrative invitations.

### 3.3 Cryptographic Failures (A02:2021)
- All communications are enforced over TLS 1.3 / HTTPS.
- Sensitive environment secrets (`JWT_SECRET`, `DB_PASSWORD`, AWS access keys) are injected exclusively at runtime via environment variables and are excluded from git version control.

### 3.4 Cross-Site Scripting (XSS) (A03:2021)
- **Frontend Protection**: React and Next.js automatically encode and sanitize all interpolated data inside JSX nodes. `dangerouslySetInnerHTML` is completely avoided across all public and admin views.
- **HTTP Response Headers**: The Nginx reverse proxy enforces:
  - `X-XSS-Protection: "1; mode=block"`
  - `X-Content-Type-Options: "nosniff"`
  - `X-Frame-Options: "SAMEORIGIN"` (Mitigates clickjacking)

### 3.5 Cross-Site Request Forgery (CSRF)
- The REST API is fully stateless and relies on the `Authorization: Bearer <token>` HTTP header rather than ambient browser cookies for sensitive state changes. Consequently, typical CSRF attack vectors are mitigated by architectural design.

### 3.6 Unrestricted File Uploads (A04:2021)
- The Media Library module enforces:
  - Strict MIME-type whitelisting (`image/png`, `image/jpeg`, `image/svg+xml`, `image/webp`, `application/pdf`).
  - Hard limit of 25MB per file upload.
  - Randomized UUID file naming upon ingestion to prevent directory traversal (`../`) attacks.

## 4. Tamper-Evident Audit Logging

All administrative mutations generate an auditable record persisted to the `audit_logs` table via `AuditLogService`:
- Timestamp (UTC)
- Actor email
- Action type (`CREATE_PRODUCT`, `UPDATE_SERVICE`, `DELETE_CAREER`, etc.)
- Client IP address
- Target entity type and UUID

Audit logs are immutable: the administrative API provides read-only pagination over audit logs with no delete or update endpoints.
